# ЛР-10. Структури папок

Ці таблиці заповнюєте ви: «У яких теках лежить кошик» — по рядку для
стартової структури (§4.3) і для гібридної (§4.7), «Вибір структури» — у
§4.8. Рядок «Пакет» — лише якщо виконуєте додаткове завдання §4.10. Як
рахувати теки, описано в інструкції, §4.2, а як подати таблиці у звіті —
у §5.

## У яких теках лежить кошик

Кошик — це шість файлів: сховище, `useCart`, `AddToCartButton`,
`CartLine`, сторінка кошика й шапка з лічильником. «Тек» — у скількох теках
вони лежать, «Теки» — шляхи цих тек через кому.

| Структура              | Тек | Теки                            |
| ---------------------- | --- | ------------------------------- |
| За типом файлів (§4.3) | 4   | components, hooks, pages, store |
| Гібридна (§4.7)        |     |                                 |
| Пакет (§4.10)          |     |                                 |

## Вибір структури

Описи проєктів, з чого обирати і як пояснити вибір — в інструкції, §4.8.
«Чому»: що в проєкті важливо і чому обрана структура для цього підходить.

| Проєкт                            | Структура                                       | Чому                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Прототип на хакатоні           | За типом файлів                                 | Найважливіше — за 24 години зібрати п’ять екранів силами трьох людей; спільними є лише кнопки й поля, тому простих тек за типом файлів достатньо. Якщо ідея переможе й застосунок виросте, структуру варто переглянути відповідно до нових залежностей.                                                                                                                                              |
| 2. Блог і документація на Next.js | За маршрутами                                   | Сорок сторінок мають власну розмітку, і щомісяця з’являються нові, тому зручно тримати код кожної сторінки біля її маршруту. Спільні шапку й підвал можна винести в shared/, а маршрути узгодити з файловою маршрутизацією Next.js.                                                                                                                                                                  |
| 3. Адмінка для бариста            | За функціональністю                             | Замовлення й склад використовуються на кількох екранах, тому важливо тримати їхні компоненти, стан і логіку разом у відповідних функціональностях. Це допоможе чотирьом розробникам протягом кількох років змінювати предметні частини без пошуку пов’язаного коду серед усіх екранів.                                                                                                               |
| 4. Інтернет-магазин кави          | Feature-Sliced Design                           | Три команди роками додають функції, а кошик, товари й акаунт потрібні на більшості сторінок, тому важливі чіткі межі відповідальності та напрямки залежностей. Шари FSD відокремлять сторінки, користувацькі дії та сутності, а публічні API слайсів обмежать залежність команд від внутрішньої реалізації чужого коду.                                                                              |
| 5. Облік обладнання               | Гібридна: за типом файлів і за функціональністю | Найважливіше — продовжувати розробку без зупинки, тому наявний код тимчасово лишається в теках за типом файлів, а нові й поступово перероблені частини групуються за функціональністю. Спільний довідник обладнання варто виділити в окрему функціональність із публічним API, щоб екрани використовували його без дублювання, а понад 150 компонентів переносити частинами під час пов’язаних змін. |
